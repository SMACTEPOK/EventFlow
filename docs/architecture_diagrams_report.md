# Лабораторна робота №2 — EventFlow Architecture Diagrams

**Дисципліна:** Проєктування архітектури, специфікація та стандарти інженерії  
**Тема:** Побудова C4 Model, UML-моделювання статичної структури та динаміки поведінки  
**Варіант:** 4 — Online Ticket Booking & Event Platform  
**Система:** EventFlow  
**Навчальний заклад:** Херсонський національний технічний університет (ХНТУ)

## 1. Мета роботи

Мета лабораторної роботи — побудувати багаторівневий архітектурний опис EventFlow із застосуванням C4 Model та UML 2.5, описати статичну структуру системи, взаємодію компонентів, бізнес-сценарії та життєвий цикл ключової доменної сутності.

Усі діаграми реалізовані як код PlantUML (Diagrams as Code). Вихідні файли збережені в `docs/diagrams/`.

## 2. Архітектурний контекст і узгодженість із ЛР №1

Модель продовжує архітектурні рішення, визначені в ЛР №1:

- архітектурний стиль — модульний моноліт із принципами Clean/Hexagonal Architecture;
- PostgreSQL — основне транзакційне джерело істини;
- Redis — допоміжне кешування та rate limiting, не джерело істини для бронювань;
- OIDC/OAuth 2.0 — стандартизована автентифікація;
- RBAC — рольова авторизація;
- RabbitMQ — асинхронна доставка подій до фонових обробників і сервісу сповіщень.

RabbitMQ та Notification Worker показані як архітектурні контейнери цільової моделі для асинхронних сповіщень. Для узгодженого запису бізнес-зміни та події може застосовуватися transactional outbox.

## 3. C4 Model

### 3.1. Level 1 — System Context

**Файл:** `docs/diagrams/c4-level1-context.puml`

Діаграма відображає EventFlow як систему в контексті зовнішніх акторів і систем.

Основні актори:
- Customer — пошук подій, вибір місць, бронювання та оплата;
- Event Organizer — керування подіями та квитковим інвентарем;
- Customer Support — підтримка та перегляд замовлень;
- Platform Administrator — адміністрування платформи.

Зовнішні системи:
- OIDC Identity Provider — автентифікація та видача/перевірка токенів;
- External Payment Provider — обробка платежів і callback-повідомлення;
- Email / Notification Provider — доставка повідомлень.

Взаємодії позначені протоколами HTTPS/JSON або OIDC/OAuth 2.0 over HTTPS.

### 3.2. Level 2 — Container Diagram

**Файл:** `docs/diagrams/c4-level2-container.puml`

Основні контейнери:
- Web Application — браузерний клієнт React + TypeScript;
- EventFlow Backend — Java + Spring Boot, модульний моноліт;
- Notification Worker — фоновий обробник асинхронних подій;
- PostgreSQL — основна реляційна БД;
- Redis — кеш і допоміжний механізм rate limiting;
- RabbitMQ — брокер повідомлень.

Зовнішні залежності: OIDC Identity Provider, External Payment Provider, Email Provider.

| Зв'язок | Протокол |
|---|---|
| Browser → Web Application | HTTPS |
| Web Application → Backend | HTTPS / JSON (REST) |
| Backend → PostgreSQL | PostgreSQL protocol over TCP/IP |
| Backend → Redis | Redis protocol over TCP/IP |
| Backend → RabbitMQ | AMQP 0-9-1 over TCP/IP |
| RabbitMQ → Notification Worker | AMQP 0-9-1 over TCP/IP |
| Backend → Payment Provider | HTTPS / JSON |
| Backend / Worker → Identity or Email Provider | HTTPS; OIDC/JWKS where applicable |

PostgreSQL є авторитетним джерелом транзакційних даних. Redis не використовується для остаточного визначення власника місця або підтвердження бронювання. Асинхронна доставка через RabbitMQ відокремлює фонові сповіщення від синхронного процесу бронювання.

## 4. UML Component Diagram

**Файл:** `docs/diagrams/uml-component-booking.puml`

Діаграма деталізує Booking Backend — ключову частину системи, що координує процес резервування.

Компоненти:
- Booking REST Controller;
- Booking Application Service;
- Reservation Domain Service;
- Seat Inventory Adapter;
- Booking Repository Adapter;
- Payment Integration Adapter;
- Event Publisher Adapter;
- Authorization Component.

Надані інтерфейси (Provided) представляють операції, які компонент надає іншим компонентам. Запитувані інтерфейси (Required) відображають залежності, які компонент використовує для виконання своєї відповідальності.

Ключові контракти:
- `IBookingUseCases` — зовнішній інтерфейс сценаріїв бронювання;
- `ISeatAvailability` — перевірка доступності місць;
- `IBookingRepository` — збереження та отримання бронювань;
- `IPaymentGateway` — інтеграція з платіжним провайдером;
- `IDomainEventPublisher` — публікація доменних подій;
- `IAuthorizationPolicy` — перевірка прав доступу.

Адаптери ізолюють доменну логіку від зовнішніх систем і технологій зберігання.

## 5. UML Domain Class Diagram

**Файл:** `docs/diagrams/uml-domain-class.puml`

Доменна модель містить вісім основних класів:
1. `Customer` — покупець;
2. `Event` — подія;
3. `Venue` — майданчик;
4. `Seat` — місце;
5. `Booking` — бронювання;
6. `BookingItem` — позиція бронювання;
7. `Payment` — платіж;
8. `Ticket` — електронний квиток.

Для атрибутів визначено специфікатори доступу та типи даних, для операцій — видимість, параметри й типи повернення. На зв'язках вказана кратність.

Композиція `Venue`—`Seat` показує, що місця є структурними частинами майданчика в межах цієї доменної моделі. Композиція `Booking`—`BookingItem` відображає володіння позиціями бронювання. Зв'язок `BookingItem`—`Seat` вказує, яке місце резервує конкретна позиція.

Ключовий інваріант: одне місце не може мати більше одного активного підтвердженого бронювання для тієї самої події. Цей інваріант має забезпечуватися транзакційними механізмами та обмеженнями БД, а не лише перевіркою на рівні інтерфейсу.

## 6. UML Sequence Diagrams

### 6.1. Сценарій 1 — Резервування місць та оплата

**Файл:** `docs/diagrams/uml-sequence-booking-payment.puml`

Учасники: Customer, Web Application, Booking API, Authorization, Booking Service, PostgreSQL, Payment Adapter, Payment Provider та RabbitMQ.

Основний потік:
1. Користувач обирає подію та місця.
2. API перевіряє токен доступу.
3. Система послідовно перевіряє кожне запитане місце.
4. За доступності всіх місць створюється тимчасове бронювання.
5. За наявності промокоду виконується додаткова перевірка.
6. Платіжний адаптер ініціює оплату.
7. Після підтвердження платежу бронювання переходить у стан CONFIRMED, а система публікує подію.

Комбіновані фрагменти:
- `alt` — невалідний токен / валідний токен; доступні місця / конфлікт; успішна оплата / відмова;
- `opt` — необов'язкова обробка промокоду;
- `loop` — перевірка кожного місця в запиті.

### 6.2. Сценарій 2 — Доступ до бронювання та повторна доставка квитка

**Файл:** `docs/diagrams/uml-sequence-booking-access.puml`

Сценарій показує перевірку автентифікації, прав власності на бронювання та необов'язковий повторний запит доставки квитка.

Комбіновані фрагменти:
- `alt` — помилка автентифікації (401), успішна автентифікація, власник бронювання / сторонній користувач (403);
- `opt` — повторне надсилання квитка, якщо квиток уже виданий.

Повторна доставка виконується асинхронно: Booking Service публікує подію в RabbitMQ, Notification Worker отримує її та звертається до Email Provider. Це не блокує основний запит перегляду бронювання.

## 7. UML State Machine Diagram

**Файл:** `docs/diagrams/uml-state-booking.puml`

Діаграма описує життєвий цикл сутності `Booking`.

Основні стани:
- Draft — чернетка;
- Held — місця тимчасово зарезервовані;
- PaymentPending — очікується результат оплати;
- Confirmed — оплату підтверджено;
- PaymentFailed — платіж не пройшов;
- Expired — час резервування минув;
- Cancelled — бронювання скасовано.

У межах стану Confirmed деталізовано підпроцес видачі квитка: TicketPending, TicketIssued та TicketError. Повторна спроба видачі квитка не повинна створювати дублікати.

Перехід до Confirmed дозволений лише після перевіреного підтвердження оплати. Перехід до Expired має атомарно звільняти тимчасово зарезервовані місця.

## 8. Відповіді на контрольні питання

### 8.1. У чому фундаментальні відмінності C4 Model та UML 2.5?

C4 Model — це підхід до опису архітектури через ієрархію рівнів абстракції: System Context, Container, Component і Code. Він орієнтований на пояснення структури системи різним аудиторіям. UML 2.5 — стандартизована мова моделювання з набором діаграм для структурних і поведінкових аспектів програмного забезпечення. C4 відповідає на питання «з яких великих частин складається система і як вони взаємодіють», а UML дає детальніші формальні засоби опису компонентів, класів, послідовностей та станів.

### 8.2. Як на C4 Container Diagram відображаються синхронні та асинхронні виклики?

Синхронна взаємодія зазвичай показується суцільною стрілкою від клієнта до сервера із зазначенням протоколу та формату, наприклад HTTPS/JSON для REST або gRPC over HTTP/2. Асинхронна взаємодія показується через брокер повідомлень: producer надсилає повідомлення до RabbitMQ або Kafka, а consumer отримує його незалежно від часу публікації. На стрілках вказуються AMQP або Kafka protocol over TCP/IP.

### 8.3. Що означають Provided та Required інтерфейси?

Provided interface — інтерфейс, який компонент надає іншим компонентам; у UML позначається лollipop («кулька»). Required interface — інтерфейс, який компонент потребує від іншого; позначається socket («розетка»). Це дає змогу явно показати контракти компонентів та їхні залежності.

### 8.4. Чим відрізняються агрегація та композиція?

Агрегація — слабкий зв'язок «ціле—частина», за якого частина може існувати незалежно від цілого. Композиція — сильне володіння: життєвий цикл частини залежить від цілого. У доменній моделі EventFlow позиції `BookingItem` моделюються композицією з `Booking`, оскільки вони є складовими конкретного бронювання. Місця `Seat` моделюються композицією з `Venue` у межах обраної моделі володіння майданчиком.

### 8.5. Як працюють alt, opt та loop у Sequence Diagram?

`alt` задає альтернативні гілки залежно від умови, наприклад успішна або неуспішна оплата. `opt` задає необов'язкову ділянку, яка виконується лише за істинності умови, наприклад застосування промокоду. `loop` описує повторювану взаємодію, наприклад перевірку кожного місця в запиті бронювання.

## 9. Підготовка до живого модифікаційного тесту

### Завдання A — додавання Notification Service

У C4 Container Diagram вже передбачено Notification Worker і RabbitMQ. Під час захисту можна пояснити, що Backend публікує події через AMQP 0-9-1, Worker споживає їх із брокера та надсилає повідомлення зовнішньому Email Provider через HTTPS/JSON. Для нових типів сповіщень додаються відповідні типи подій і обробники.

### Завдання B — помилка авторизації 401

У першій Sequence Diagram уже передбачено `alt` для невалідного або відсутнього токена з відповіддю `401 Unauthorized`. У другій Sequence Diagram також є окрема гілка для невдалої автентифікації. Під час демонстрації можна змінити умову або додати повідомлення про повторну автентифікацію.

## 10. Висновки

У результаті лабораторної роботи побудовано архітектурну модель EventFlow з використанням C4 Model та UML. Розроблено контекстну діаграму системи, контейнерну діаграму з конкретними технологіями й мережевими протоколами, компонентну діаграму Booking Backend із Provided та Required інтерфейсами, доменну діаграму класів із типами, специфікаторами доступу та кратністю зв'язків.

Також побудовано два сценарії послідовностей із комбінованими фрагментами `alt`, `opt` і `loop`, а також діаграму станів життєвого циклу бронювання. Модель узгоджена з архітектурними рішеннями ЛР №1 та може бути використана як основа для подальшої деталізації архітектури й реалізації.

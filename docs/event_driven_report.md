# Лабораторна робота №5
## Реалізація Event-Driven Architecture для EventFlow

### 1. Мета роботи

Реалізувати подієво-орієнтовану взаємодію компонентів системи EventFlow. Забезпечити асинхронну публікацію інтеграційних подій, незалежну роботу споживачів та ідемпотентну обробку повторних повідомлень.

### 2. Архітектурне рішення

У межах лабораторної роботи продовжено реалізацію EventFlow з лабораторної роботи №4. Застосовано внутрішню шину подій InMemoryEventBus, яка реалізує Observer-подібну модель підписки та асинхронної диспетчеризації.

Application залежить від абстракції IEventPublisher та контрактів інтеграційних подій. Application не залежить від Messaging, Infrastructure, RabbitMQ, Kafka або конкретної транспортної бібліотеки.

Проєкт Messaging містить реалізацію шини подій, механізм підписки та споживачів. Поточна реалізація використовує внутрішню пам'ять процесу і призначена для демонстрації архітектурних принципів, а не для міжпроцесної доставки повідомлень.

### 3. Контракти подій

У проєкті src/Events визначено два контракти:

- BookingCreatedEvent — створення бронювання;
- PaymentProcessedEvent — успішна обробка платежу.

Кожна подія містить EventId, OccurredAtUtc та AggregateId. Додаткові поля містять дані, необхідні відповідному сценарію.

BookingCreatedEvent публікується безпосередньо з CreateBookingUseCase після успішного збереження бронювання в репозиторії.

PaymentProcessedEvent визначено як контракт для наступного сценарію платіжної інтеграції. У цій лабораторній роботі окремий платіжний процесор не реалізовано.

### 4. Публікація подій

CreateBookingUseCase отримує IEventPublisher через конструктор. Послідовність виконання:

1. Створення та валідація сутності Booking.
2. Перевірка доступності місць.
3. Збереження бронювання через IBookingRepository.
4. Формування BookingCreatedEvent з унікальним EventId, UTC-часом та ідентифікатором бронювання.
5. Публікація події через IEventPublisher.
6. Повернення результату операції.

Якщо перевірка місць або збереження завершується помилкою, подія не публікується.

### 5. Споживачі подій

Для BookingCreatedEvent реалізовано два незалежні споживачі:

- BookingNotificationConsumer — демонстрація обробки події для сповіщення;
- BookingAnalyticsConsumer — демонстрація обробки події для аналітики.

Шина подій запускає обробники незалежно. Помилка одного споживача перехоплюється на рівні його диспетчеризації та не перешкоджає запуску інших підписників.

### 6. Ідемпотентність

Для зберігання ідентифікаторів оброблених подій використано IProcessedEventStore та InMemoryProcessedEventStore.

Ключ ідемпотентності формується з імені споживача та EventId. Тому кожен споживач має власний стан обробки однієї події.

IdempotentConsumer використовує блокування для пари споживач-подія. Перед виконанням перевіряється наявність EventId у сховищі. Ідентифікатор записується як оброблений лише після успішного завершення ProcessAsync. Якщо обробка завершується помилкою, подія не позначається обробленою та може бути повторена.

### 7. Перевірка роботи

Автоматизовані тести перевіряють:

- публікацію BookingCreatedEvent після успішного збереження;
- відсутність публікації у разі помилки репозиторію;
- одноразову обробку повторно доставленої події кожним споживачем;
- незалежність споживачів у разі помилки одного з них;
- можливість повторної обробки після невдалого виконання споживача.

Демонстраційна програма публікує BookingCreatedEvent, очікує завершення асинхронних обробників, повторно публікує ту саму подію та демонструє пропуск дубліката.

### 8. Обмеження реалізації

InMemoryEventBus та InMemoryProcessedEventStore зберігають стан лише в пам'яті поточного процесу. Вони не забезпечують довготривале зберігання, повторну доставку після перезапуску, транзакційний Outbox або міжпроцесну доставку. Для промислової експлуатації доцільно використати брокер повідомлень і персистентне сховище ідемпотентності.

### 9. Висновок

У системі EventFlow реалізовано базову подієво-орієнтовану взаємодію. Основний сценарій створення бронювання публікує інтеграційну подію після збереження. Два незалежні споживачі обробляють подію асинхронно. Повторна доставка не спричиняє повторного виконання успішно обробленої події, а помилка одного споживача не блокує іншого.

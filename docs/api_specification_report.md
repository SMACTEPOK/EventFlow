## 2. Мета роботи

Розробити контрактно-орієнтовані API для EventFlow: публічний REST API на основі OpenAPI 3.0.3 та внутрішній gRPC API на основі Proto3. Перевірити REST-контракт, згенерувати Java stubs, порівняти розміри JSON і Protobuf та оцінити сумісність контрактів під час змін.

## 3. Архітектурний контекст

У попередніх лабораторних роботах для EventFlow було обрано модульний моноліт із принципами Clean/Hexagonal Architecture та PostgreSQL як основним сховищем.

У цій роботі визначено два контрактні інтерфейси:

- **REST Booking API** — публічний інтерфейс для вебклієнта, мобільного клієнта та зовнішніх споживачів.
- **gRPC Inventory API** — типізований внутрішній інтерфейс взаємодії модуля Booking з підсистемою Inventory.

Виділення Inventory в окремий сервіс є можливою еволюцією архітектури, але саме по собі не змінює прийнятого архітектурного стилю модульного моноліту.

Застосовано підхід Contract-First: визначення інтерфейсів зберігаються незалежно від реалізації. Реалізації та клієнтські/серверні stubs мають відповідати контрактам, а не навпаки.

## 4. REST API: OpenAPI 3.0.3

Основний файл: `api/openapi.yaml`.

Контракт використовує OpenAPI 3.0.3, JSON для успішних відповідей, Bearer JWT для автентифікації та заголовок `X-Request-ID` для кореляції запитів.

### 4.1. Операції

| Метод | Endpoint | Призначення | Основна успішна відповідь |
|---|---|---|---|
| GET | `/v1/bookings` | Отримання списку бронювань із фільтрами та пагінацією | 200 |
| POST | `/v1/bookings` | Створення бронювання | 201 |
| GET | `/v1/bookings/{bookingId}` | Отримання бронювання за UUID | 200 |
| PATCH | `/v1/bookings/{bookingId}` | Оновлення змінюваних атрибутів бронювання | 200 |
| DELETE | `/v1/bookings/{bookingId}` | Скасування/видалення бронювання за контрактом | 204 |

Параметри списку бронювань:
- `status` — фільтр за статусом;
- `eventId` — фільтр за подією;
- `limit` — кількість елементів на сторінці, від 1 до 100, типове значення 20;
- `cursor` — курсор для отримання наступної сторінки.

### 4.2. DTO та валідація

Основні схеми контракту:
- `BookingStatus`;
- `Booking`;
- `CreateBookingRequest`;
- `UpdateBookingRequest`;
- `BookingListResponse`;
- `PaginationMetadata`;
- `Problem`;
- `FieldValidationError`.

`CreateBookingRequest` вимагає `eventId` у форматі UUID та масив `seatIds`. Масив має містити від 1 до 10 унікальних UUID. `promoCode` є необов'язковим і перевіряється за шаблоном великих латинських літер і цифр.

У схемах задані типи, обмеження та приклади значень.

### 4.3. Обробка помилок

Для помилок використовується RFC 7807 Problem Details із типом вмісту `application/problem+json`.

Основні поля:
- `type` — URI, що ідентифікує тип проблеми;
- `title` — короткий заголовок;
- `status` — HTTP-статус;
- `detail` — пояснення конкретної помилки;
- `instance` — URI конкретного випадку;
- додаткові поля `code` та `errors` можуть містити машинний код і перелік помилок валідації.

Контракт описує відповіді 400, 401, 404 та 422, а також внутрішню помилку 500.

### 4.4. Безпека та кореляція

Для захищених операцій визначено Bearer Authentication із JWT. `X-Request-ID` використовується для зв'язування запиту з журналами та трасуванням у різних компонентах.

## 5. Перевірка REST-контракту

### 5.1. Spectral

OpenAPI перевірено за допомогою Spectral CLI з ruleset `.spectral.yaml`, який успадковує `spectral:oas`.

Під час першої перевірки було виявлено відсутній опис операції `getBooking`. Опис додано до OpenAPI-файлу, після чого повторна перевірка завершилася повідомленням:

`No results with a severity of 'error' found!`

Отже, помилок рівня error не виявлено.

### 5.2. Prism Mock Server

Для запуску mock-сервера використано:

```powershell
npx --yes @stoplight/prism-cli mock api/openapi.yaml --host 127.0.0.1 --port 4010 --errors --verboseLevel info
```

Mock-сервер опубліковано локально на `http://127.0.0.1:4010`.

Prism повертає приклади, визначені контрактом. Це перевірка інтерфейсу, а не реалізація повноцінної бізнес-логіки, бази даних або стану бронювання.

### 5.3. Інтеграційні перевірки

Тести збережено в `api/tests/test-api.ps1`.

| Сценарій | Очікуваний статус | Фактичний статус | Результат |
|---|---:|---:|---|
| Коректний POST створення бронювання | 201 | 201 | PASS |
| POST із некоректним payload | 422 | 422 | PASS |
| GET із фільтрами та параметрами пагінації | 200 | 200 | PASS |
| GET з `limit=101` | 422 | 422 | PASS |

Підсумок виконання: **4 із 4 тестів пройшли успішно**.

Важливе обмеження: Prism повертає статичні приклади. Під час тесту GET із `limit=10` у прикладі відповіді було повернуто `pagination.limit=20`. Це не підтверджує реалізацію фактичної пагінації; воно демонструє, що mock-відповідь є прикладом із контракту, а не результатом обробки запиту реальною системою.

## 6. gRPC API: Proto3

Основний файл: `api/service.proto`.

Пакет: `eventflow.inventory.v1`.  
Java package: `com.eventflow.inventory.v1`.

Контракт визначає сервіс `InventoryService` з такими RPC:

| RPC | Тип виклику | Призначення |
|---|---|---|
| `CheckAvailability` | Unary | Перевірка доступності місць |
| `ReserveSeats` | Unary | Резервування місць |
| `WatchReservationStatus` | Server streaming | Потокове отримання подій статусу резервування |
| `CancelOperation` | Unary | Скасування операції |

### 6.1. Типізація повідомлень

У повідомленнях застосовано:
- `string` — ідентифікатори та текстові значення;
- `int64` — цілі числові значення;
- `double` — грошова сума;
- `bool` — логічні прапорці;
- `google.protobuf.Timestamp` — часові мітки;
- вкладені повідомлення для структурованих даних;
- `repeated` для списків.

Переліки `AvailabilityStatus` і `ReservationStatus` починаються зі значення `*_UNSPECIFIED = 0`, що відповідає рекомендаціям Proto3.

### 6.2. Генерація Java stubs

Використано:
- `protoc` 36.2;
- `protoc-gen-grpc-java` 1.85.1.

Результат: 22 Java-файли у `api/generated/java/com/eventflow/inventory/v1/`.

Перевірено наявність `CancelOperation` у `InventoryServiceGrpc.java` та значення `RESERVATION_STATUS_CANCELLED = 5` у `ReservationStatus.java`.

Proto3-контракт перевірено компілятором `protoc` із генерацією descriptor set; синтаксична перевірка пройшла успішно.

Згенеровані файли є вихідним кодом stubs. Їх не слід вважати скомпільованим або розгорнутим сервісом: для компіляції потрібен Java build із відповідними залежностями Protobuf і gRPC runtime.

## 7. Порівняння JSON та Protobuf

Для порівняння використано одне логічне повідомлення `ReserveSeatsResponse` з однаковими значеннями: ідентифікатор резервування, статус, час завершення резервування, сума та валюта.

Результати збережено у `api/benchmark/benchmark-results.json`.

| Показник | JSON UTF-8 | Protobuf binary |
|---|---:|---:|
| Розмір повідомлення | 148 байтів | 41 байт |

Розрахунок економії:

`148 - 41 = 107 байтів`

`107 / 148 × 100 = 72,30%`

Співвідношення розмірів:

`148 / 41 = 3,61`

Отже, у цьому тестовому прикладі Protobuf займає на 72,30% менше місця, ніж JSON, або JSON-повідомлення у 3,61 раза більше.

Protobuf binary payload було повторно декодовано за допомогою `protoc`; значення полів збіглися з початковими.

Обмеження експерименту: виміряно лише розмір серіалізованого payload. Не враховано TLS, транспортні заголовки, HTTP/gRPC framing, стиснення та мережеві затримки. Це вимірювання розміру, а не CPU benchmark.

### 7.1. Якісне порівняння

| Критерій | JSON / REST | Protobuf / gRPC |
|---|---|---|
| Розмір | Більший для цього прикладу | Менший для цього прикладу |
| Читабельність | Висока, текстовий формат | Нижча у бінарному вигляді |
| Типізація | Схема OpenAPI та JSON Schema | Строга схема Proto3 |
| Еволюція схеми | Потребує сумісності API та DTO | Нумеровані поля підтримують сумісну еволюцію за дотримання правил |
| Транспорт | Зазвичай HTTP/1.1 або HTTP/2 | HTTP/2 |
| Типові сценарії | Публічні API, браузери, інтеграції | Внутрішні сервісні виклики, streaming |

Висновок: REST/JSON зручний для зовнішніх споживачів і налагодження. gRPC/Protobuf доцільний для типізованої внутрішньої взаємодії та потокових сценаріїв. Результат одного вимірювання не є універсальним коефіцієнтом для всіх повідомлень.

## 8. Перевірка еволюції контрактів

### 8.1. Модифікація A — пагінація REST

До `GET /v1/bookings` додано параметри:
- `limit` із максимально допустимим значенням 100;
- `cursor` для продовження вибірки.

Також визначено `PaginationMetadata` з полями `limit`, `nextCursor` та `hasMore`.

Перевірка граничного значення `limit=101` через Prism повернула HTTP 422. Отже, обмеження параметра присутнє в контракті та перевіряється mock-сервером.

### 8.2. Модифікація B — CancelOperation у gRPC

До `InventoryService` додано unary RPC `CancelOperation`, повідомлення запиту та відповіді, а також статус `RESERVATION_STATUS_CANCELLED = 5`.

Після зміни повторно згенеровано Java stubs. У згенерованих файлах перевірено наявність нового RPC та enum-значення.

Поточні номери вже наявних полів і числові значення інших enum-елементів збережено. Це важливо для сумісності з попередніми повідомленнями.

## 9. Відповіді на контрольні питання

### 9.1. У чому перевага Contract-First?

Contract-First дозволяє узгодити формат запитів, відповідей, помилок і типів до початку реалізації. Клієнтські та серверні команди можуть працювати паралельно на основі стабільного інтерфейсу. Контракт також дає змогу автоматизувати перевірки, документацію, mock-сервери та генерацію коду.

### 9.2. Як Protobuf використовує Varint і field tags?

Кожне поле Protobuf кодується з тегом, що містить номер поля та wire type. Номер поля і тип визначають, як декодувати значення. Цілі числа для сумісних wire types можуть кодуватися Varint — способом змінної довжини, який використовує менше байтів для невеликих значень.

Номер поля є частиною формату даних, тому його не можна довільно змінювати після використання контракту.

### 9.3. Чому у Proto3 немає required і які правила сумісності?

Proto3 не використовує звичайний `required` для полів повідомлень. Це зменшує ризик несумісності, коли старий споживач отримує нове повідомлення з невідомими або відсутніми полями.

Рекомендації:
- не змінювати номер уже опублікованого поля;
- не повторно використовувати номери видалених полів;
- видалені номери та імена за потреби резервувати через `reserved`;
- нові поля додавати з новими номерами;
- не змінювати тип поля без перевірки wire compatibility;
- обережно змінювати значення enum і зберігати нульове значення `UNSPECIFIED`.

### 9.4. Які поля RFC 7807 є обов'язковими і чому plain error string — anti-pattern?

Стандарт RFC 7807 визначає поля `type`, `title`, `status`, `detail` та `instance`. Вони є стандартизованими членами Problem Details, але не всі є обов'язковими для кожного документа: `type` має значення `about:blank`, якщо не заданий; інші поля можуть бути відсутніми залежно від ситуації. У цьому контракті `type`, `title` та `status` зроблено обов'язковими.

Звичайний рядок помилки не має стабільної структури, машинного коду та стандартизованого HTTP-статусу. Клієнтам доводиться аналізувати текст, що є ненадійним. Problem Details дозволяє клієнту обробляти помилки структуровано.

### 9.5. Які переваги HTTP/2 порівняно з HTTP/1.1 для gRPC?

HTTP/2 підтримує мультиплексування кількох потоків в одному TCP-з'єднанні, бінарне фреймування та стиснення заголовків HPACK. Це зменшує накладні витрати на повторні заголовки та дозволяє ефективно підтримувати двосторонні й потокові RPC.

HTTP/1.1 не має такого стандартного мультиплексування потоків в одному з'єднанні. gRPC використовує HTTP/2 як транспортну основу.

## 10. Висновки

У роботі визначено публічний REST-контракт Booking API у форматі OpenAPI 3.0.3 та внутрішній gRPC-контракт InventoryService на Proto3.

OpenAPI пройшов перевірку Spectral без помилок. Чотири сценарії REST-тестування через Prism завершилися успішно. Proto3 пройшов синтаксичну перевірку, а Java stubs були згенеровані у кількості 22 файлів.

У тестовому порівнянні JSON payload мав розмір 148 байтів, а Protobuf — 41 байт, що відповідає економії 72,30%. Це підтверджує перевагу Protobuf за розміром у межах конкретного прикладу, але не є вимірюванням продуктивності CPU чи повної мережевої затримки.

Також перевірено два сценарії еволюції контрактів: обмеження пагінації REST та додавання RPC скасування операції в gRPC із повторною генерацією stubs.

Таким чином, мету лабораторної роботи досягнуто на рівні проєктування, валідації контрактів, mock-тестування та генерації вихідного коду.

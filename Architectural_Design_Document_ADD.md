## 1. Вступ та цілі системи

### 1.1. Призначення документа

Цей Architectural Design Document (ADD) узагальнює архітектурні рішення EventFlow, результати лабораторних робіт №1–6, структурні та поведінкові моделі, API-контракти, подієву взаємодію та фізичне розгортання.

Документ використовує структуру arc42 і термінологію ISO/IEC/IEEE 42010. Він розрізняє цільову архітектуру платформи та фактично реалізований навчальний прототип.

### 1.2. Призначення системи

EventFlow — платформа для пошуку подій і бронювання квитків на концерти, спортивні змагання та інші заходи.

Цільові бізнес-можливості:
- пошук і перегляд подій;
- перегляд конфігурації майданчика та місць;
- перевірка доступності місць;
- тимчасове резервування та створення бронювання;
- інтеграція з платіжними провайдерами;
- випуск електронних квитків;
- сповіщення клієнтів;
- адміністрування подій та інвентарю.

### 1.3. Архітектурні цілі

1. Забезпечити цілісність процесу бронювання та запобігти подвійній видачі місць.
2. Розділити бізнес-правила, прикладну логіку та інфраструктурні адаптери.
3. Підтримати незалежне тестування бізнес-сценаріїв.
4. Забезпечити контрольовану інтеграцію з зовнішніми провайдерами.
5. Підтримати асинхронну обробку інтеграційних подій.
6. Зберегти простоту початкового розгортання через модульний моноліт.
7. Документувати обмеження навчального прототипу та умови переходу до production.

### 1.4. Межі реалізації

У лабораторному прототипі реалізовано створення бронювання через REST API, доменну валідацію, in-memory репозиторій, адаптер доступності місць, публікацію `BookingCreatedEvent`, асинхронний InMemory EventBus і два незалежні idempotent consumers.

Платіжний процес, реальна доставка електронної пошти, OIDC-аутентифікація, PostgreSQL і Redis не підключені до поточного виконуваного прототипу.

## 2. Архітектурні обмеження та вимоги якості

### 2.1. Архітектурні обмеження

- Основний архітектурний стиль — Modular Monolith.
- Усередині застосунку застосовуються Clean/Hexagonal Architecture.
- Доменний шар не залежить від інфраструктури.
- Application залежить від Domain та контрактів подій.
- Infrastructure реалізує порти, визначені прикладним і доменним шарами.
- WebAPI є точкою входу HTTP-запитів.
- EventBus реалізує асинхронну диспетчеризацію подій у межах одного процесу.
- У лабораторному розгортанні використовується один контейнер застосунку.
- Фактичний runtime — .NET 8 / ASP.NET Core.
- Docker Compose описує тільки сервіси, які реально реалізовані та підключені.

### 2.2. Вимоги якості (ISO/IEC 25010)

| Характеристика | Архітектурний підхід | Статус підтвердження |
|---|---|---|
| Functional suitability | Use case створення бронювання, доменна валідація | Перевірено unit-тестами для прототипу |
| Performance efficiency | Мінімізація внутрішніх мережевих викликів; асинхронні consumers | Не проводилося production load testing |
| Compatibility | REST/JSON API та окремі контракти подій | Контракти створено; зовнішні інтеграції не підключені |
| Interaction capability | HTTP API та стандартні відповіді | Локальний API-прототип |
| Reliability | Ізоляція помилок consumers, idempotency за EventId | Перевірено тестами; збереження стану volatile |
| Security | Цільова стратегія OIDC/OAuth 2.0, RBAC, HTTPS | У прототипі не налаштовано |
| Maintainability | Clean Architecture, інтерфейси портів, модульні проєкти | Перевірено структурою залежностей і тестами |
| Flexibility | Адаптери та контрактна інтеграція | Архітектурно передбачено |

### 2.3. Кількісні цілі цільової системи

Цільові NFR, визначені в лабораторній №1:
- до 5 000 одночасних користувачів;
- орієнтир до 200 API-запитів за секунду;
- p95 каталогу подій — до 500 мс;
- p95 карти місць — до 1 000 мс;
- p95 створення бронювання — до 2 000 мс без часу зовнішньої оплати;
- цільова доступність — 99,9%;
- RPO — до 15 хвилин;
- RTO — до 2 годин.

Ці показники є архітектурними цілями, а не результатами вимірювання поточного навчального прототипу.

## 4. Архітектурна стратегія та ADR

### 4.1. Архітектурний стиль

Обрано Modular Monolith із принципами Clean/Hexagonal Architecture.

Переваги:
- чіткі межі відповідальності;
- локальні виклики між модулями;
- простіше тестування;
- контрольована складність розгортання;
- можливість подальшого виділення сервісів за наявності обґрунтованої потреби.

### 4.2. Структура шарів

| Шар | Відповідальність |
|---|---|
| Domain | Сутності, інваріанти та доменні правила |
| Application | Use cases, порти, координація сценаріїв |
| Infrastructure | Реалізація репозиторіїв та зовнішніх адаптерів |
| WebAPI | HTTP-контролери, маршрути та композиція залежностей |
| Events | Контракти інтеграційних подій |
| Messaging | EventBus, consumers, idempotency store |

### 4.3. Dependency Rule

Залежності спрямовані до внутрішніх шарів:
- Domain не посилається на Application, Infrastructure або WebAPI.
- Application посилається на Domain та Events.
- Infrastructure реалізує порти Application і працює з Domain.
- WebAPI збирає залежності та надає HTTP-вхід.
- Messaging реалізує механізм диспетчеризації подій і посилається на Application та Events.

### 4.4. Architecture Decision Records

| ADR | Рішення |
|---|---|
| ADR-0001 | Modular Monolith та Clean/Hexagonal Architecture |
| ADR-0002 | PostgreSQL як цільове authoritative storage; Redis як supporting cache |
| ADR-0003 | OIDC/OAuth 2.0 та RBAC як цільова security strategy |
| ADR-0004 | Один контейнер .NET 8 із внутрішнім InMemory EventBus для лабораторного прототипу |

Повні записи рішень розміщено в `docs/adrs/`.

### 5.2. Доменна модель

Основна доменна сутність — `Booking`.

Створення бронювання проходить доменну перевірку:
- EventId не повинен бути порожнім;
- CustomerId не повинен бути порожнім;
- кількість місць має бути в межах 1–10;
- колекція SeatIds не повинна бути порожньою;
- ідентифікатори місць мають бути унікальними.

### 5.3. Межі відповідальності

`CreateBookingUseCase` координує перевірку доступності, збереження бронювання та публікацію інтеграційної події. Репозиторій і публікатор подій передаються через інтерфейси. WebAPI не реалізує бізнес-правила.

## 6. Динамічна взаємодія: API, послідовності та події

### 6.1. REST API

Основний маршрут:
`POST /v1/bookings`

Вхідний DTO:
- `EventId`;
- `CustomerId`;
- `SeatIds`.

Успішний результат — HTTP 201 Created із даними бронювання. Доменна помилка повертається як HTTP 400, недоступність місць — як HTTP 422.

API-контракт лабораторної №3 розміщено в `api/openapi.yaml`. Контракт є специфікацією API; фактична реалізація прототипу має обмежений набір операцій.

### 6.2. Подієві контракти

`IIntegrationEvent` містить:
- EventId;
- OccurredAtUtc;
- AggregateId.

Реалізовані контракти:
- `BookingCreatedEvent`;
- `PaymentProcessedEvent` (контракт визначено, але платіжний workflow не реалізований).

### 6.3. Сценарій створення бронювання

1. Клієнт надсилає POST `/v1/bookings`.
2. `BookingsController` формує `CreateBookingCommand`.
3. `CreateBookingUseCase` викликає доменну фабрику `Booking.Create`.
4. Перевіряється доступність місць через `ISeatAvailabilityPort`.
5. Бронювання зберігається через `IBookingRepository`.
6. Після успішного збереження публікується `BookingCreatedEvent`.
7. EventBus асинхронно диспетчеризує подію двом підписникам.
8. Notification consumer виконує демонстраційну обробку сповіщення.
9. Analytics consumer виконує демонстраційну аналітичну обробку.
10. Кожен consumer перевіряє EventId у своєму просторі імен споживача та пропускає повторну доставку.

### 6.4. Обробка помилок та ідемпотентність

Помилки одного consumer ізолюються від іншого. EventId позначається обробленим тільки після успішного завершення обробки. Повторна доставка того самого EventId не повинна спричиняти повторну зміну стану.

У поточній реалізації processed-event store зберігається в пам'яті процесу. Для production потрібне стійке сховище ідентифікаторів оброблених подій та надійна доставка.

### 6.5. gRPC

`api/service.proto` визначає контракт InventoryService. Генеровані Java stubs є артефактом лабораторної №3; вони не входять до поточного .NET runtime і не є розгорнутим сервісом.

### 7.3. Docker Compose

Файл `compose.yaml` описує один сервіс `eventflow-api`, який збирається з кореневого `Dockerfile` і публікує порт 8080.

Команди запуску:
```powershell
docker compose build
docker compose up -d
docker compose ps
Invoke-RestMethod http://localhost:8080/health
```

Перевірка створення бронювання:
```powershell
$body = @{
    eventId = [guid]::NewGuid().ToString()
    customerId = [guid]::NewGuid().ToString()
    seatIds = @(
        [guid]::NewGuid().ToString(),
        [guid]::NewGuid().ToString()
    )
} | ConvertTo-Json

Invoke-RestMethod `
    -Uri "http://localhost:8080/v1/bookings" `
    -Method Post `
    -ContentType "application/json" `
    -Body $body
```

Перегляд логів:
```powershell
docker compose logs -f eventflow-api
```

Очікувані записи після POST-запиту: `[PUBLISH]`, `[NOTIFICATION]`, `[ANALYTICS]`, `[PROCESSED]`. Порядок завершення двох consumers може відрізнятися, оскільки вони запускаються незалежно.

### 7.4. Обмеження поточного розгортання

- Репозиторій бронювань зберігає дані в оперативній пам'яті.
- Idempotency store також є volatile.
- Перезапуск контейнера призводить до втрати стану.
- EventBus не забезпечує durable delivery.
- HTTPS, OIDC, PostgreSQL, Redis, платіжний та email-адаптери не налаштовані.
- Один контейнер не забезпечує високу доступність.
- Наведені NFR є цілями, а не доведеними характеристиками прототипу.

## 8. Компроміси, ризики та подальший розвиток

### 8.1. Архітектурні компроміси

| Рішення | Перевага | Компроміс |
|---|---|---|
| Modular Monolith | Простота розгортання та локальні транзакції | Спільний lifecycle модулів |
| InMemory repository | Простота демонстрації | Втрата даних після перезапуску |
| InMemory EventBus | Немає зовнішнього брокера | Немає durable delivery |
| Два consumers в одному процесі | Незалежна логіка обробки | Немає незалежного масштабування |
| Один Docker container | Мінімальна конфігурація | Єдина точка відмови |
| PostgreSQL/Redis як target | Визначена стратегія зберігання | Потрібні адаптери та інтеграційні тести |

### 8.2. Основні ризики

1. **Втрата бронювань:** замінити InMemory repository на PostgreSQL-адаптер із транзакційними обмеженнями.
2. **Втрата подій:** реалізувати transactional outbox і durable message transport.
3. **Повторна обробка:** зберігати processed EventId у стійкому сховищі з атомарною перевіркою.
4. **Несанкціонований доступ:** налаштувати OIDC, перевірку токенів і RBAC.
5. **Перевантаження:** виконати навантажувальні тести, оптимізувати запити й масштабувати екземпляри.
6. **Недоступність одного вузла:** додати health monitoring, резервування та процедури відновлення.
7. **Відмова зовнішніх інтеграцій:** реалізувати timeout, retry, circuit breaker та обробку webhook.

### 8.3. План подальшого розвитку

- Реалізувати PostgreSQL persistence adapter і міграції.
- Реалізувати Redis для кешу та rate limiting, не використовуючи його як джерело істини для бронювання.
- Додати transactional outbox і брокер повідомлень за обґрунтованої потреби.
- Реалізувати OIDC/OAuth 2.0 та RBAC.
- Підключити платіжного й email-провайдера через адаптери.
- Додати TLS, секрети, структуровані логи, метрики та трасування.
- Провести навантажувальні й recovery-тести для перевірки NFR.

## Додаток B. Критерії узгодженості

- Кожен вузол розгортання відповідає реальному сервісу або середовищу.
- Кожен артефакт діаграми відповідає наявному проєкту або DLL.
- Протокол і порт HTTP узгоджені з Dockerfile та Compose.
- EventBus і consumers розгортаються в одному процесі.
